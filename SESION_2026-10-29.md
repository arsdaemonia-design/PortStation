## Resumen de lo trabajado

### Plataformas compatibles

- Se añadió al modelo de proyectos el campo `supported_platforms`, que contiene los sistemas operativos para los que el proyecto ofrece una compilación o soporte declarado.
- Se añadió `supported_platforms_complete`, que indica si la lista se ha comprobado como completa. Esto permite distinguir “solo Windows” confirmado de “por ahora solo encontramos Windows”.
- La información viaja por los modelos Rust, la conversión del registro/catálogo, el DTO enviado a React y los tipos de TypeScript.
- La sincronización del catálogo conserva o completa esos campos para instalaciones existentes de acuerdo con las reglas de merge existentes.
- Se incorporaron etiquetas de compatibilidad a las fichas pertinentes y se añadió el filtro **Corre en** en Explorar Ports. Las opciones contemplan Windows, Linux, macOS, Android, multiplataforma y fichas sin datos de sistema.
- “Plataforma original” describe la consola o sistema de origen del juego. “Corre en” describe dónde se puede ejecutar el port. Son datos distintos.
- Las listas parciales no deben interpretarse como exclusivas: un proyecto sin Linux registrado no equivale necesariamente a “solo Windows”.

### Variantes de Breath of the Wild

Se separó el proyecto Android de dos alternativas orientadas a PC para que el registro Android no se confunda con compatibilidad de escritorio:

- **BOTWRecompAndroid:** se mantiene como proyecto Android.
- **Savage Wind Recomp:** entrada independiente para Windows y Linux; proyecto alfa/WIP.
- **BotW-Native:** entrada independiente para Windows; proyecto WIP.

Las fichas de PC se muestran como proyectos en desarrollo y no deben presentarse como ports terminados. Las notas de sesión identifican sus plataformas declaradas; el avance y los requisitos deben revisarse en sus repositorios antes de describirlos como jugables.

### Decisión sobre descargas de otras plataformas

Se descartó añadir en Configuración un selector general para habilitar descargas de sistemas operativos ajenos al dispositivo. La recomendación es mostrar las descargas compatibles con el sistema actual y mantener el repositorio/releases como acceso informativo para quien necesite otro artefacto. El filtro **Corre en** sirve para descubrir compatibilidad del proyecto; no convierte una compilación de Windows en ejecutable en Linux o macOS.

## Cómo funciona el aviso de actualización de PortStation

La aplicación consulta los releases públicos del repositorio configurado. El valor por defecto que aparece en el código es:

`https://github.com/arsdaemonia-design/PortStation`

En el arranque se ejecuta la comprobación y también hay una comprobación manual en Configuración. El código considera primero releases estables; si no hay ninguno, utiliza prereleases. Compara el tag con la versión compilada en PortStation y clasifica los assets por sistema operativo según sus nombres y extensiones.

Cuando encuentra una versión posterior, muestra el aviso de actualización. Al pulsar la descarga, la aplicación abre el enlace del asset en el navegador. **El actualizador actual no instala ni reemplaza la aplicación silenciosamente**: el usuario descarga el archivo y aplica la actualización manualmente. El usuario verá el aviso la próxima vez que abra una versión de PortStation que incluya esta comprobación.

## Publicar una versión para que aparezca el aviso

La página de publicación es [GitHub Releases de PortStation](https://github.com/arsdaemonia-design/PortStation/releases). El flujo actual requiere preparar y adjuntar los artefactos; el workflow de CI existente solo ejecuta comprobaciones/build y no publica automáticamente instaladores. Además, `src-tauri/tauri.conf.json` tiene `bundle.active` desactivado.

1. **Revisar y guardar los cambios del código.** Ejecutar las verificaciones acordadas y confirmar que la app abre desde el paquete que se va a entregar.
2. **Elegir la siguiente versión SemVer.** Por ejemplo, si la instalada es `0.1.0`, usar `0.1.1` para una corrección o `0.2.0` para una entrega con funciones nuevas. El tag de GitHub puede escribirse `v0.1.1`; el comparador elimina el prefijo `v`.
3. **Sincronizar el número de versión** en estos tres archivos antes de compilar:
   - `package.json` → `version`
   - `src-tauri/Cargo.toml` → `package.version`
   - `src-tauri/tauri.conf.json` → `version`

   Para que el aviso compare correctamente, los tres deben tener exactamente la misma versión que el tag que se publicará. Rust incorpora la versión de `Cargo.toml` al binario mediante `CARGO_PKG_VERSION`.
4. **Generar el artefacto distribuible** de Windows y, si corresponde, los artefactos Linux/macOS/Android. Para una versión portable, empaquetar la carpeta ejecutable y sus recursos en ZIP, sin incluir archivos temporales ni datos privados. El nombre debe identificar claramente plataforma y arquitectura, por ejemplo `PortStation-windows-x64.zip`; si se publica un instalador, adjuntar el `.exe`/`.msi` generado. La clasificación de assets reconoce extensiones habituales como `.exe`, `.msi`, `.zip`, `.AppImage`, `.deb`, `.dmg` y `.apk`, y también palabras como `windows`, `linux`, `macos` o `android`.
5. **Crear un release en GitHub:** abrir Releases → **Draft a new release**; crear o seleccionar el tag nuevo (`v0.1.1`), elegir la rama/commit que contiene el código versionado, escribir título y notas, y adjuntar los artefactos correspondientes. Publicar el release, no dejarlo como draft.
6. **Comprobarlo con una instalación anterior.** Abrir una compilación que tenga una versión menor; en el inicio o en Configuración debe aparecer la nueva versión. Probar que el botón lleva al asset correcto para Windows. La comparación depende de que el tag sea una versión SemVer interpretable.

### Diferencia entre publicar la app y publicar el catálogo

| Quiero actualizar… | Qué publicar | Qué verá el usuario |
| --- | --- | --- |
| PortStation (el programa) | Un GitHub Release con tag SemVer nuevo y artefactos adjuntos | Aviso de nueva versión al abrir una app anterior; descarga manual desde navegador |
| Explorar Ports (los registros) | `src-tauri/ports_db.json` en la ruta remota que consulte la app, con `catalog_version` incrementada | Nueva versión del catálogo al sincronizarlo; no instala una versión nueva de PortStation |

Subir un JSON nuevo no hace que el actualizador de la aplicación lo trate como release. Crear un release sin adjuntar el instalador/ZIP adecuado puede hacer que aparezca la versión, pero dejar al usuario sin un artefacto descargable para su sistema.

## Actualización de la sesión: opinión sobre Android y versión de app

### Opinión sobre la propuesta de Android

La dirección general es válida: Tauri v2 permite reutilizar React y buena parte de Rust, y el entorno Android se puede compilar en local o en CI. La hoja de ruta pegada es un buen borrador, pero **no significa que PortStation ya esté listo para Android ni que el APK vaya a funcionar sin adaptar el producto**.

- La única preparación móvil comprobada en el código actual es el atributo `#[cfg_attr(mobile, tauri::mobile_entry_point)]`. No se encontró `src-tauri/gen/android/` inicializado ni un workflow Android en `.github/workflows`.
- `launch_game` y el modelo de ejecutable están orientados al escritorio. Android requeriría registrar identificadores de paquete e invocar aplicaciones externas con APIs/Intents nativos; los `.exe` no se ejecutan ahí.
- Las rutas de carpeta, permisos y el acceso a medios externos necesitan un diseño para Android. El filesystem Android está aislado por sandbox y los permisos/scopes deben concederse explícitamente; añadir `MANAGE_EXTERNAL_STORAGE` a ciegas no es una estrategia adecuada.
- También falta evaluar la interfaz táctil en pantallas pequeñas, el ciclo de vida móvil, descarga/instalación de APKs y qué funciones de escritorio se ocultan o adaptan.
- GitHub Actions puede hacer compilaciones repetibles, pero primero hay que configurar el workflow, targets Rust, SDK/NDK, firma y artefactos. No es automáticamente más rápido para llegar a un primer prototipo. Como el usuario ya tiene Android Studio, sugiero usar un build local temprano para detectar errores de integración y después mover builds repetibles a Actions.
- La afirmación de que Java 25 necesariamente fallará está desactualizada como regla general: la compatibilidad depende de la versión de Tauri/Gradle del proyecto; la documentación actual de Tauri 2.12 indica que su plantilla Gradle 9 admite Java 25. Verificar la plantilla/versión concreta antes de cambiar Java.

**Recomendación:** tratar Android como un objetivo de producto aparte con alcance inicial pequeño: instalar/abrir PortStation, mostrar catálogo, filtrar por Android y abrir una app de juego ya instalada. No incluir en el primer APK un scanner recursivo de carpetas de ports de escritorio ni descargar/ejecutar binarios arbitrarios.

Referencias oficiales consultadas: [Prerequisitos de Tauri](https://v2.tauri.app/start/prerequisites/), [Tauri Filesystem](https://v2.tauri.app/plugin/file-system/), [distribución Google Play](https://v2.tauri.app/distribute/google-play/), [Tauri 2.12 y Java 25](https://v2.tauri.app/de/blog/tauri-2.12/).
